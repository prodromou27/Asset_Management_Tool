## Recorded implementation assumptions

| ID | Assumption | Guardrail |
|---|---|---|
| ASM-01 (Task 001) | Backend pinned to Django 5.2 LTS (5.2.18 at bootstrap); 5.1 is end-of-life. Revisit the LTS line before 5.2 support ends (April 2028). | `pyproject.toml` bounds `django>=5.2.18,<5.3`; uv.lock committed. |
| ASM-02 (Task 001) | SQLite is allowed **only** as an opt-in shortcut for running the backend test suite on a workstation without Docker (`ITAM_TEST_DB_SQLITE=1`, `config.settings.test`). PostgreSQL is mandatory for Docker development, CI, staging and production. | Fallback exists only in test settings; raises if `CI` is set; CI fails on any skipped PostgreSQL/Redis integration test; a test asserts the engine is PostgreSQL unless the opt-in is set. |

| ASM-03 (Task 002) | Local accounts only. **No local TOTP/MFA yet** and no OIDC; Entra is listed as `planned` by `/auth/providers`. Per docs/09, privileged local access must stay restricted (internal network, named admins, no public exposure) until DEC-11 is decided. | Production readiness gate: DEC-11 must be resolved (IdP MFA or reviewed local TOTP) before go-live. |
| ASM-04 (Task 002) — **closed in Task 003** | Site scoping implemented: users have `all_sites` or explicit `UserSiteGrant`s; a grant on a site includes its child sites. All asset reads go through `assets.selectors.visible_assets(user)`; out-of-scope IDs return 404 and out-of-scope site/location IDs in payloads return the same 422 as unknown IDs. Department scoping is **not** implemented (departments are org-wide reference data). | Cross-site denial tests cover list, filters, detail, history, PATCH, archive, restore, classification (and preview) and create/reassign. Future export/report jobs must start from `visible_assets()`. |
| ASM-05 (Task 002) | Role definitions are seeded and read-only in V1 UI; editing role→permission grants is not exposed yet. System Admin must always keep users.manage/users.view/roles.view/audit.view (`MANDATORY_ADMIN_PERMISSIONS`). | Enforce the mandatory set when role editing is added. |
| ASM-06 (Task 002) | Audit events are append-only: model guard + PostgreSQL trigger blocks UPDATE/DELETE/TRUNCATE. Retention purge (future) must run under a separate, audited maintenance role. | Trigger is created by migration `audit.0002`; tested in CI on PostgreSQL. |
| ASM-07 (Task 002) | Frontend API types are generated with openapi-typescript 6.7.x because 7.x requires the TypeScript 5 compiler API, which TypeScript 7 (native) does not expose. | CI fails if `schema.d.ts` or `openapi.yaml` drift from the backend schema. Revisit when openapi-typescript supports TS 7. |

| ASM-08 (Task 003) | Asset owner is an ITAM user account (FK). People who are not users cannot be owners yet; directory/HR sync is a later integration. Owner choices come from `GET /users/lookup/` (active users; id, username, display name only). | Revisit with Entra/M365 directory objects (Task 010). |
| ASM-09 (Task 003) — **closed in Task 004** | Field-level rights: business fields need `assets.edit`; technical fields (manufacturer, model, serial, OS name/version, firmware) supplied by a discovery source need `assets.edit_technical` (ITAM Manager, Infrastructure Engineer, System Admin). Asset Operators may still edit technical values that were only ever entered manually. Lock/unlock and conflict resolution need `assets.edit_technical`. | Enforced in `assets.services.check_field_permissions`; tested per role (403 `FIELD_PERMISSION_DENIED` with field list). |
| ASM-10 (Task 003) | Custom field values are stored in `Asset.custom_fields` (JSONB) and validated against typed definitions on write. Definitions inherit down the category tree; key and type are immutable. Values that stop applying after reclassification are retained read-only, never dropped. Required fields are enforced on create and reclassification; ordinary edits report `missing_required_fields` instead of blocking unrelated changes. | If reporting needs typed SQL filtering on custom fields, add typed value tables or expression indexes. |
| ASM-11 (Task 003) | Manufacturer/model are free text until the vendor/model catalogue (Task 015). Observation and support status are read-only via the API (defaults `manual_only`, `unknown`) and will be set by discovery and the EOL engine. | Catalogue task links assets to canonical models without dropping the free-text values. |
| ASM-12 (Task 003) | Manual network identifiers (hostnames, interfaces/MACs, IPs) are edited as replace-sets of `source="manual"` rows only; rows from other sources are never modified by manual edits. No global uniqueness on IP, MAC, hostname or serial. | Task 004 writes discovered rows with their source, reference and observed time. |

| ASM-13 (Task 004) | Discovery never creates, deletes or merges assets by itself. New devices become reconciliation candidates; a person links, creates, holds or rejects. Only a verified manufacturer+serial or hardware-UUID match with agreeing category may auto-link, and only when the instance's `auto_link_strong_matches` is switched on (default off). IP, hostname, MAC or model alone never link. | Matching rules in `reconciliation/matching.py`; tests cover each rule and docs/15 A01–A04, A08. |
| ASM-14 (Task 004) | Connectors will emit an adapter-neutral *source record* (fixtures/discovery/README.md). Until adapters exist, records enter only through the operator-run `manage.py load_observations` command; there is deliberately no HTTP ingestion endpoint. Vendor sources are seeded as Planned. | Each adapter task (006–010) maps its API payload to this record and calls `reconciliation.services.ingest`. |
| ASM-15 (Task 004) | Observations are immutable and stored only when the payload checksum (excluding `observed_at`) changes; unchanged reports refresh last-seen only. Raw payload retention is unbounded for now. | Retention policy (docs/14: Defender raw data) to be set with DEC-15. |
| ASM-16 (Task 004) | Field authority: manual locks beat all sources; between sources the configured per-field precedence decides while the higher source's link is active; a stale source loses authority. Lower-authority disagreements are shown as "differs" evidence, not as conflicts; only locked fields open conflicts. | Precedence editable under Administration → Integrations (audited). |
| ASM-17 (Task 004) | A full sync marks unseen links stale only if the run had zero errors; partial runs never mark anything stale. The hourly freshness task marks links stale after the instance threshold. Assets are never archived or deleted for missing sources. | Celery beat `refresh-source-freshness`. |
| ASM-18 (Task 004) | Merges move source links and discovered identifiers to the survivor and archive the duplicate; manual identifiers, custom fields and history stay with the duplicate. Revert moves the recorded rows back. Merging does not re-apply observations; the next sync does. | Revisit if a merge needs to combine manual data. |

| ASM-19 (Task 005) | Saved views store only filter keys (allowlisted), visible columns and ordering. Personal by default; sharing needs `assets.edit`; only the owner changes or deletes a view. A shared view is re-applied through `visible_assets()` for each viewer, so it never widens site scope. Column choices without a view are kept per user in browser storage; column widths are not persisted. | Server-side per-user preferences can replace browser storage if roaming profiles are needed. |
| ASM-20 (Task 005) | Inventory search uses PostgreSQL `pg_trgm` GIN indexes on `UPPER(col)` (the expression Django's `icontains` generates) for name, tag, serial, manufacturer, model and hostname; related-table conditions use `EXISTS` (no `DISTINCT`). CI asserts list, count and four search shapes each finish under 1.5 s at 10k assets. This is a single-request approximation, not the docs/14 p95 load test. | Full load test belongs to Task 022 on AlmaLinux staging. Indexes were created non-concurrently; on a large live table rebuild them concurrently. |

| ASM-21 (Task 006) | Two independent gates guard every live connector call: the deployment setting `ITAM_ALLOW_LIVE_INTEGRATIONS` (default false) and a per-integration approval recorded by an administrator with a reason (audited approve/revoke). Connection tests and syncs are refused with a clear code otherwise. | Keep the setting false until the Docker-host verification passes and DEC-05 supplies an approved read-only account. |
| ASM-22 (Task 006) | API tokens are never stored in the database or returned by the API. An integration stores a reference: `env:ITAM_INTEGRATION_<NAME>` (the prefix stops references to unrelated process secrets) or `file:<name>` directly inside `ITAM_SECRETS_DIR`. The UI shows only Not set / Invalid / Secret not found / Secret available. A private CA bundle may be given as a `file:` reference; TLS verification cannot be disabled. | Rotate by changing the env/secret file and restarting api/worker. |
| ASM-23 (Task 006) | The LibreNMS client can only send GET requests under `/api/v0`, refuses redirects, requires `https://`, and refuses targets that resolve to loopback, link-local (including cloud metadata), multicast, unspecified or reserved addresses; private RFC 1918 ranges are allowed. `Authorization: Bearer` is the default header; `X-Auth-Token` (the header documented by LibreNMS) is selectable. Which one the installed version accepts must be confirmed with a connection test. | Verify with the approved account during live validation (DEC-05). |
| ASM-24 (Task 006) | LibreNMS is **Beta**: implemented and tested only against sanitized fixtures shaped from the API v0 documentation. Optional routes (per-device IPs, ports, inventory, FDB, links) are detected from the `GET /api/v0` route listing and skipped with a warning when absent. Field names must be compared with the installed version's real (sanitized) responses before relying on scheduled sync. | Promote to Available only after live validation; capture sanitized real fixtures then. |
| ASM-25 (Task 006) | Request budget: each sync reads `GET /devices` once; per-device details (IPs, ports limited to IP-bearing interfaces, `inventory/{id}/all`) are re-read only for new devices, when LibreNMS `last_discovered` changes or after `enrichment_max_age_hours`. FDB and LLDP/CDP links are read every `evidence_interval_hours` (default 24). Requests are rate-limited (default 5/s) with retries, exponential backoff and `Retry-After`. Volatile poller fields are kept out of the observation checksum, so unchanged devices do not create new observations. | Scale target 2,000–10,000 devices is a design figure, not load-tested; measure on staging (Task 022). |
| ASM-26 (Task 006) | FDB and LLDP/CDP data are stored as `NeighborEvidence` (observed, never a confirmed physical cable). LibreNMS FDB `vlan_id` is its internal VLAN row id, not the 802.1Q tag; port names are known only for cached IP-bearing ports (otherwise "port N"). A complete evidence pass retires rows that were not seen; a pass with a missing capability retires nothing. The asset view caps evidence at 500 rows. | Revisit with a topology task if VLAN tags or full port names are needed. |
| ASM-27 (Task 006) | LibreNMS timestamps carry no zone; they are interpreted in the integration's `source_timezone` (default UTC) and stored as UTC. A device whose `last_polled` is missing uses the sync time with a warning. Devices disabled in LibreNMS are still reported (with a warning) so they are not marked stale. | Set the zone per instance to the LibreNMS server zone. |
| ASM-28 (Task 007) | Connectors share one read-only HTTP client (`adapters/http.py`: GET only, TLS verified, no redirects, SSRF checks, rate limit, retries) and register in `adapters/registry.py`; a source can be synchronised only if registered. Each connector declares its allowed auth headers (validated on save) and whether it has an evidence pass. | New adapters (Tasks 008–010) plug into the registry; nothing else in the sync engine changes. |
| ASM-29 (Task 007) | Endpoint Central is **Beta**. The API generation is chosen by handshake: `GET /dcapi/inventory/viewData/scanComputers` first, then `GET /api/1.4/inventory/scancomputers` (page size 1); the first returning a recognisable computer list wins and is stored as a capability. Field names, the `dcapi` envelope, pagination parameter names (`page`/`pageLimit`, `page`/`pagelimit`) and the header format (raw `Authorization: <key>` by default; Bearer selectable) come from documentation examples and sanitized fixtures, not from a live server. Fields are looked up by a short list of key names anywhere in the detail document, so modest schema drift is tolerated; unknown values stay unknown. | Confirm with sanitized responses from the installed build (DEC-06) before enabling the schedule; adjust `endpoint_central/mapping.py` key lists if they differ. |
| ASM-30 (Task 007) | Endpoint Central request budget: the computer list in pages of 500; per computer, details are re-read only when it is new, Endpoint Central reports a newer successful scan, or after `enrichment_max_age_hours` (1 request on api/1.4; up to 4 on dcapi). Installed software, monitors and peripherals are **not** read yet (software belongs to Task 016). A listing that fails after page 1, repeats a page or returns fewer computers than its reported total is processed but treated as incomplete: nothing is marked stale. | Measure list and detail timings on staging (Task 022). |
| ASM-31 (Task 007) | Endpoint Central mapping: the scan time is `last_successful_scan` (epoch ms/s, ISO or naive in `source_timezone`), falling back to the agent contact time with a warning. Category hints come only from the reported chassis or a server OS or hypervisor model; anything else is left for the reviewer. OEM placeholder manufacturer, model and serial values are treated as unknown. Interface names may contain `( ) # + ,` (Windows adapter names); this also applies to manual entry. Only identifying adapter values (name, MAC, IPs) are stored as raw provenance, so lease times and free-space counters do not create new observations. | Revisit when real payloads are reviewed. |
| ASM-32 (Task 007a, ADR-013) | Strong-match gate. A strong key (verified manufacturer + serial, or a hardware UUID reported by another linked source) is auto-linked only when the instance allows it **and** the manufacturer is known on both sides and the same (after normalisation), the category root is known on both sides and the same, and nothing contradicts it. Contradictions make the candidate `conflict` (proposed asset kept for the reviewer): a different manufacturer or category, a different serial on the asset, a hardware UUID that differs from what other linked sources report, or other assets sharing two or more identifier families. A serial that matches an asset of another manufacturer is shown as a `conflicting` key and a `conflict` candidate instead of a silent new device. Unknown manufacturer or category leaves a `strong` candidate for review. MAC, hostname and IP differences are not treated as contradictions (NIC swaps, renames and DHCP are normal). | Revisit if reviewers report too many conflicts. |

## Change-control rule for agents

If a decision would change data identity, security, deployment, scope or business semantics, propose a short ADR with context, options, decision and consequences. Do not silently choose a dangerous default. For cosmetic/local code choices within approved architecture, decide and proceed.
